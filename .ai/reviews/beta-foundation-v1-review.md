# Beta Foundation V1 Independent Review

## Executive verdict

**Verdict: FAIL.** Beta Foundation V1 must not be treated as accepted or used as the foundation for the next milestone until the Critical/High release blockers in the required follow-up register are completed and independently re-reviewed.

The repository at `7f72313` contains real implementation of the three tables, job-based visual generation, reload restoration, memory writes, usage recording, and test scaffolding. However, several milestone claims are materially overstated: the migration chain cannot create a fresh project; an already-committed migration was edited after introduction; browser-authenticated users receive excessive mutation authority over jobs and memories and can fabricate usage records; active-job uniqueness, memory superseding, and job transitions are not database-enforced; the flashcard threshold is only a page-local counter; and no tests exercise these claims. Authenticated cross-user RLS isolation remains unverified.

No production access or mutation was performed. The review was conducted on 2026-07-29 against the repository state at `7f72313` (`main` and `origin/main`). The target commit itself mostly adds governance and Playwright material; the foundation implementation entered through `aa14f4b`, `3418b66`, and `208a1d7` and is merely contained in the tree at `7f72313`.

## Claims confirmed

- **Confirmed — generation jobs exist.** The migration defines `generation_jobs`; the visuals route creates and updates a job; the status route returns an authenticated user's matching job.
- **Confirmed — user memories exist.** The migration and server actions implement user-scoped reads, inserts, soft deletion, and category filtering.
- **Confirmed — usage events exist.** The migration defines an append-only-at-policy-level table and application call sites record several generation outcomes.
- **Confirmed — VisualsPanel uses job polling.** It checks on mount, polls `/api/jobs/status/:id` every three seconds, stops on terminal client-observed states, and refreshes `study_visuals` on completion.
- **Confirmed — reload restoration is attempted.** When no SSR visuals exist, the panel asks for the newest job for the user/document/type and resumes polling for queued/processing rows.
- **Confirmed — stale-job UX exists.** A client-side ten-minute processing threshold changes the panel to a retry state.
- **Confirmed — duplicate prevention is attempted.** UI state blocks an additional click in one mounted panel and the route cancels active rows before inserting a replacement.
- **Confirmed — quiz performance and weakness memory calls exist.** Quiz completion writes a document performance memory and knowledge memories for incorrectly answered concepts.
- **Confirmed — flashcard preference memory call exists.** A page-local completion counter triggers a preference-memory write from the third completion onward.
- **Confirmed — MemoryCategory is aligned in the target tree.** TypeScript and the current migration both allow `activity`, `knowledge`, `preference`, `performance`, and `engagement`.
- **Confirmed — RLS and basic CHECK constraints are present in SQL.** RLS is enabled for all three new tables; status/type/category/score checks exist.
- **Confirmed — unit and Playwright files exist.** This confirms test scaffolding, not the behavioral/security claims below.

## Claims only partially confirmed

- **High — milestone report accuracy cannot be fully assessed.** No permanent milestone report was present. The supplied delivered-scope list is accurate as a list of code paths but overstates safety, reproducibility, idempotency, and verification. **Owner:** Beta Foundation implementer + milestone lead. **Completion:** before milestone re-review; provide a corrected, evidence-linked report.
- **High — migration safety for the current live database is unproved.** `CREATE TABLE IF NOT EXISTS` silently preserves any incompatible pre-existing table definition; the SQL has no preflight for existing objects/data/grants/policies and no live schema/grant dump. Policy replacement is transactional if run as one transaction, but the file instructs manual section execution. **Owner:** Database architect. **Completion:** before any further production migration or rollout approval.
- **High — fresh-project reproducibility is false.** The only migration references `public.documents`, but no migration creates it (or the other application schema/storage contracts). Applying this repository's migration chain to a fresh Supabase project will fail at the first `REFERENCES documents(id)` unless manual state is supplied. **Owner:** Database architect. **Completion:** before the next milestone begins.
- **High — RLS ownership expressions are plausible but not proved.** The policies use `auth.uid() = user_id`, and the implicit `WITH CHECK` for `FOR ALL` prevents changing a row to another user. But policies are not role-scoped, grants were not captured, existing additional permissive policies were not enumerated, RLS is not forced, and authenticated two-user negative tests do not exist. **Owner:** Security engineer + database architect. **Completion:** before beta release and before next milestone acceptance.
- **Medium — reload restoration is incomplete.** It is skipped whenever SSR returns any existing visuals, even if a regeneration job is active; the UI can therefore show old visuals without restoring the active regeneration state. **Owner:** Frontend engineer. **Completion:** before claiming full reload restoration.
- **High — stale-job handling does not mark a job stale.** It only changes client state; the database row stays `processing`. Retrying then cancels it regardless of whether the original invocation is still working. **Owner:** Job-platform/backend engineer. **Completion:** before production reliance on background jobs.
- **High — duplicate-job prevention is not safe.** There is no active-status unique constraint or atomic claim/create operation. UI guards are tab-local; concurrent requests can both cancel/check and insert. **Owner:** Database architect + backend engineer. **Completion:** before next milestone begins (A1).
- **High — weakness-memory superseding is neither reliable nor atomic.** It deactivates rows using a wildcard content match, then separately queries/updates/inserts. Concurrent requests can leave no active row, create duplicates, or supersede unrelated content containing the same concept text. **Owner:** Database architect + intelligence engineer. **Completion:** before memory data informs personalization.
- **High — flashcard `>=3` threshold does not prove three durable sessions.** The counter starts at zero on every page load, counts only completions in that mount, has no durable session identity, and can be incremented repeatedly by repeating the final-card completion path. It can undercount across reloads and double-count within a page. **Owner:** Intelligence engineer + database architect. **Completion:** before preference memories are used for adaptation.
- **Medium — polling works but has no backoff or coordination.** Every open panel polls every three seconds through a server route which performs authentication and a database read; multiple tabs multiply load, network errors poll forever, and the route supplies no cache validators or push mechanism. **Owner:** Frontend/platform engineer. **Completion:** before broad beta or defined scale testing.

## Security findings

- **Critical — SEC-01: authenticated clients have excessive `generation_jobs` authority.** `FOR ALL` lets a user insert arbitrary own jobs and update/delete every column of own rows directly through the browser Supabase client, including `status`, `result_data`, `error`, timestamps, document association, type, and correlation ID. This destroys the trustworthiness of job state and allows forged terminal results. Parent ownership is not enforced by a composite FK or policy check, so a user permitted to insert can probe/reference another user's document ID subject to FK behavior. **Owner:** Database security engineer. **Completion:** before release/re-review.
- **Critical — SEC-02: usage records can be fabricated and duplicated.** Any authenticated client can insert arbitrary own `generation_type`, token/image counts, success, model, duration, correlation ID, document ID, and timestamp (default only, not immutable from explicit insert). There are no type/range checks, parent-ownership check, idempotency key, or unique constraint; the correlation index is non-unique. These rows are unsuitable for entitlements, billing, abuse controls, or audit. **Owner:** Database security engineer + billing/entitlements owner. **Completion:** before usage data affects limits, analytics, billing, or release acceptance.
- **High — SEC-03: authenticated users can mutate/delete their own memory records without server-controlled semantics.** `FOR ALL` permits direct insert/update/delete of content, metadata, confidence, importance, source, active status, and timestamps. That is incompatible with treating memories as trustworthy system-derived intelligence unless explicitly designed as user-editable data with provenance separation. **Owner:** Intelligence/security engineer. **Completion:** before memories drive adaptation.
- **High — S1: authenticated cross-user RLS isolation remains unverified.** Current supplied live evidence covers anonymous isolation only. No two authenticated user test proves User B cannot SELECT, INSERT against User A parent IDs, UPDATE, or DELETE User A rows in any of the three tables. **Owner:** Security QA + database architect. **Completion:** before next milestone begins and before beta release.
- **High — SEC-04: error details can leak through API/UI and logs.** The worker stores raw exception messages in `generation_jobs.error`; the status API returns the error; VisualsPanel renders it. Visual generation errors can contain provider/configuration/storage detail. Separate `console.error` calls log raw provider/storage messages and public storage URLs outside the structured logger's key-based redaction. **Owner:** Security engineer + backend engineer. **Completion:** before release.
- **Medium — SEC-05: generated study visuals are public URLs.** `getPublicUrl` is used for potentially personal study material. The migration does not create/reconcile the bucket or its policies, so confidentiality, enumeration, overwrite isolation, retention, and reproducibility are unproved. **Owner:** Storage security architect; **decision owner:** George for public/private product policy. **Completion:** decision and verified policy before beta release.
- **Medium — SEC-06: source entity ownership is not enforced for memories.** `source_entity_id` is free text and no policy/FK verifies that the referenced document/recording/concept belongs to the user. **Owner:** Database architect. **Completion:** before cross-entity memory retrieval or personalization expands.

## Architecture findings

- **Critical — ARC-01: repository migrations are not a reproducible database contract.** A single manually-run SQL file depends on pre-existing `documents` and unversioned application tables/storage. This violates the repository-truth and reproducibility requirements. **Owner:** Database architect. **Completion:** before next milestone begins.
- **High — ARC-02: an introduced migration was edited in place.** `aa14f4b` introduced the migration with obsolete memory categories; `208a1d7` changed that same file. If the first version was applied live, rerunning the edited file cannot replace the existing CHECK because `CREATE TABLE IF NOT EXISTS` skips it. The target repository can therefore disagree with live schema. **Owner:** Database architect + release manager. **Completion:** immediately; inspect approved non-production/live catalogs only with George's exact approval, then use a new forward-only reconciliation migration.
- **High — ARC-03: job transitions have no state machine.** Any allowed actor can move any owned job between any enumerated statuses, including terminal-to-processing, and timestamps/result/error consistency is unconstrained. Worker updates do not condition on expected prior state, so a cancelled job can later become processing/completed when its original callback finishes. **Owner:** Backend/job-platform engineer + database architect. **Completion:** before job framework reuse.
- **High — ARC-04: `after` is an invocation-lifetime task, not a durable queue.** The route returns before completion, but work remains bounded by the configured/platform maximum duration (300 seconds) and has no lease, heartbeat, retry worker, recovery scanner, or exactly-once contract. A process/platform interruption leaves queued/processing rows stranded. **Owner:** Platform architect. **Completion:** before claiming durable background processing or scaling beyond controlled beta.
- **High — A1: duplicate active-job race.** The cancel-then-insert sequence and `getActiveJobForDocument` application read provide no concurrency guarantee. PostgreSQL supports a partial unique index for exactly this invariant, combined with an atomic server-side claim/reuse operation. **Owner:** Database architect + backend engineer. **Completion:** before next milestone begins.
- **High — ARC-05: memory identity is underspecified and non-unique.** The lookup omits absent optional fields rather than matching `NULL`, uses `maybeSingle`, and no unique constraint backs the intended identity. Multiple active matches cause the call to fall through to another insert; concurrent calls race. **Owner:** Database architect + intelligence engineer. **Completion:** before memory engine acceptance.
- **Medium — ARC-06: usage correlation does not enforce idempotency.** The migration comment says the index prevents retry double-counting, but it is a non-unique lookup index and application writes do not query it. **Owner:** Entitlements/backend engineer. **Completion:** before usage-based decisions.
- **Medium — ARC-07: generic server actions enlarge mutation surface.** `updateJobStatus`, `saveMemory`, and `recordUsage` are server actions with caller-controlled payloads; `updateJobStatus` does not authenticate explicitly or constrain ownership in its query. RLS may filter the latter under a request client, but the contract is not least-privilege and can be accidentally reused unsafely. **Owner:** Backend/security engineer. **Completion:** before reuse in future milestones.

## Reliability and performance findings

- **High — REL-01: stale detection can invalidate legitimate work.** A fixed ten-minute client clock threshold has no heartbeat/progress/lease basis. Slow provider queues or large operations can be labelled stale; retry cancels the row, while the original callback can still complete and overwrite cancellation. **Owner:** Job-platform engineer. **Completion:** before beta release.
- **High — REL-02: memory superseding is race-prone and can lose truth.** Deactivate/query/update-or-insert spans multiple requests without a transaction, lock, stable supersession key, or uniqueness constraint. **Owner:** Database architect + intelligence engineer. **Completion:** before personalization uses these memories.
- **High — REL-03: flashcard session evidence is not durable/idempotent.** There is no immutable session table/event identity or unique completion token. Repeated UI actions and concurrent tabs can generate inconsistent progress and preference claims. **Owner:** Intelligence engineer + database architect. **Completion:** before preference inference ships.
- **Medium — REL-04: polling has linear per-tab database/API cost.** At three seconds, one active tab produces about 20 authenticated API/database reads per minute; there is no exponential backoff, visibility pause, shared-tab coordination, or realtime/event delivery. **Owner:** Frontend/platform engineer. **Completion:** before load testing and wider beta.
- **Medium — REL-05: polling requests can overlap.** `setInterval` does not wait for the prior fetch; a slow status endpoint can create concurrent requests and out-of-order state handling. **Owner:** Frontend engineer. **Completion:** before wider beta.
- **Medium — REL-06: terminal completion may precede durable visual retrieval in the UI.** The worker sets completed after saving visuals, but `refreshVisuals` ignores errors and the panel sets `completed` even when no row was retrieved, potentially rendering no completed state content. **Owner:** Frontend engineer. **Completion:** before release.
- **Medium — REL-07: retention and growth are undefined.** Jobs, memories, usage events, error strings, JSON payloads, and public visual objects lack retention/archive/size policies. This conflicts with privacy, performance, and billion-user ambitions. **Owner:** Data/platform architect; **decision owner:** George for retention. **Completion:** before production-scale planning.
